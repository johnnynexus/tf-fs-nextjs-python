# Architecture

## Components

| Component        | Technology                | Where it runs                     |
| ---------------- | ------------------------- | --------------------------------- |
| Dashboard data   | USGS earthquake feed      | fetched by the backend, cached 60s |
| Frontend         | Next.js 15 (App Router)   | Cloud Run (container)             |
| Backend          | FastAPI + uvicorn         | Cloud Run (container)             |
| Database         | PostgreSQL 16             | Cloud SQL, private IP — optional  |
| Images           | Docker                    | Artifact Registry                 |
| Secrets          | generated by Terraform    | Secret Manager                    |
| Terraform state  | —                         | GCS, versioned, natively locked   |
| CI/CD            | GitHub Actions            | OIDC → Workload Identity Federation |

## Request flow

### Server-side render

```
Browser ──GET /──► Cloud Run: frontend
                      └─ Server Component calls BACKEND_INTERNAL_URL/health
                         ──► Cloud Run: backend ──► (optional) Cloud SQL
                      └─ HTML returned with the result already rendered
```

### Browser-initiated API call (default path)

```
Browser ──GET /api/backend/hello?name=x──► Cloud Run: frontend
                                              └─ route handler forwards to
                                                 BACKEND_INTERNAL_URL/api/v1/hello
                                                 ──► Cloud Run: backend
```

Same-origin, so no CORS preflight, and the backend URL is never exposed to the
browser.

### Browser-initiated API call (opt-in direct path)

```
Browser ──GET https://backend-…run.app/api/v1/hello──► Cloud Run: backend
```

Requires `NEXT_PUBLIC_API_BASE_URL` at image build time and the frontend's
origin in the backend's `CORS_ORIGINS`.

## Why the proxy is the default

`NEXT_PUBLIC_*` environment variables are substituted into the client bundle
during `next build`. The backend's Cloud Run URL is only known after
`terraform apply`. Baking the URL into the image therefore requires:

```
build image → apply → learn backend URL → rebuild image → apply again
```

Reading the target at request time on the server removes that cycle
entirely — one image, valid in every environment, and the URL becomes an
ordinary runtime env var that Terraform sets on the service.

## Backend structure

```
app/
  core/config.py     every env var, declared and typed (pydantic-settings)
  services/usgs_service.py  I/O split from pure aggregation, so the maths
                     is unit-tested against a fixture with no network
  core/logging.py    plain console locally, JSON for Cloud Logging elsewhere
  db/base.py         declarative base + created/updated timestamp mixin
  db/session.py      async engine, session dependency, connection probe
  models/            SQLAlchemy ORM models
  schemas/           pydantic request/response models
  routers/           HTTP layer — thin, delegates to services
  services/          business logic, testable without HTTP
  main.py            app factory, CORS, lifespan
```

Routers stay thin so the logic can be tested directly; `services/` has no
FastAPI imports.

## The database is an optional dependency

The backend is written so the database can be absent:

| Condition            | `/health` | `/health/ready`            | `/api/v1/items` |
| -------------------- | --------- | -------------------------- | --------------- |
| No `DATABASE_URL`    | 200       | 200, `"database":"disabled"` | 503            |
| Database reachable   | 200       | 200, `"database":"ok"`      | 200             |
| Database down        | 200       | 200, `"database":"error"`, status `degraded` | 500 |

Two consequences:

1. Terraform can default `enable_database = false` and still deploy a working
   service, so a dev environment costs nothing.
2. A database outage degrades the service instead of taking it down. Startup
   does not fail, and the liveness probe (which hits `/health`, not
   `/health/ready`) does not restart containers.

## Probes

| Probe    | Frontend        | Backend    | Rationale                                       |
| -------- | --------------- | ---------- | ----------------------------------------------- |
| Startup  | `/api/health`   | `/health`  | No traffic until the app answers.                |
| Liveness | `/api/health`   | `/health`  | Restart only a genuinely broken container.       |

Neither liveness probe touches a downstream dependency. A liveness failure
restarts the container, so making it depend on the backend or the database
would convert a dependency outage into a restart loop.

## Security posture

- **No long-lived cloud credentials.** GitHub Actions authenticates with an
  OIDC token exchanged for a short-lived GCP credential. The federation is
  scoped by `attribute_condition` to a single repository.
- **Per-service runtime identities.** Each Cloud Run service gets its own
  service account with a minimal role set. The default Compute Engine service
  account — shared and over-privileged — is not used.
- **Secrets by reference.** The database password is generated by Terraform,
  stored in Secret Manager, and mounted into Cloud Run as a secret reference.
  The plaintext never appears in the service definition.
- **No public database.** Cloud SQL has private IP only; the backend reaches
  it over direct VPC egress.
- **Non-root containers.** Both images run as an unprivileged user.
- **Terraform state is sensitive** — it contains the generated password. The
  state bucket enforces uniform access control, blocks public access, and
  keeps object versions.

## Cost

With the defaults (scale to zero, no database), an idle environment costs
approximately nothing: Cloud Run bills per request, the VPC and subnet are
free, and Artifact Registry charges only for storage (bounded by cleanup
policies).

Costs appear when you opt in:

| Choice                        | Rough monthly cost      |
| ----------------------------- | ----------------------- |
| `min_instances = 1` (per service) | ~$10–15             |
| `enable_database = true` (db-f1-micro) | ~$8            |
| Cloud SQL `REGIONAL` (HA)     | roughly double the above |
| Serverless VPC connector      | ~$9 — avoided by using direct VPC egress |
